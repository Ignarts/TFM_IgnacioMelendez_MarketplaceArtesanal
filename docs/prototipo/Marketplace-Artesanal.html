Propuesta desarrollada · Opción 3

Marketplace de Productos Artesanales

Una plataforma multivendedor donde cada usuario puede comprar y, si lo desea, abrir su propia tienda para vender piezas hechas a mano. El TFM gira en torno a la seguridad por roles y a un sistema de reputación y confianza entre desconocidos.

Spring Boot · API REST Spring Security · RBAC + JWT Spring Data JPA · MySQL MongoDB (eventos) Angular · Guards · Reactive Forms JUnit · Karma · Docker

El qué y el porqué

Concepto y propuesta de valor

Pensemos en algo tipo Etsy a pequeña escala: artesanos (cerámica, joyería, cuero, ilustración…) publican sus productos y los compradores los descubren, valoran y "adquieren" mediante un checkout simulado. La diferencia clave frente a una tienda normal es que el mismo usuario puede ejercer dos papeles y que la confianza no la da una gran marca, sino la reputación de cada pequeño vendedor.

◆El problema

En una tienda de un solo dueño, la confianza es implícita. En un marketplace, ¿cómo confío en un vendedor que no conozco? Ese es el reto que da sustancia al TFM.

◆La solución

Roles bien definidos, verificación de vendedores, valoraciones honestas e insignias por trayectoria. La plataforma "fabrica" confianza mediante software.

◆Por qué como TFM

Obliga a usar Spring Security a fondo, a modelar datos no triviales y a tomar decisiones de arquitectura defendibles en la memoria.

Sin pagos reales. El checkout es simulado (se genera un pedido con estado PENDIENTE → PAGADO → ENVIADO → ENTREGADO), igual que recomienda tu profesor. Toda la complejidad interesante (roles, stock, reputación, pedidos) se mantiene; solo se omite la pasarela de pago real.

Objetivos del proyecto (orientados a tu CV)

  • Demostrar autorización por roles (RBAC) con Spring Security, JWT y @PreAuthorize.
  • Diseñar un modelo de datos relacional realista con relaciones 1:N y N:N.
  • Construir una SPA en Angular con guards, resolvers, interceptores y formularios reactivos.
  • Implementar un sistema de reputación con justificación teórica (el "twist").
  • Cubrir tests en backend (JUnit/Mockito) y frontend (Jasmine/Karma).
  • Entregar un despliegue reproducible con Docker Compose y CI básico.

Quién usa la plataforma

Actores y roles

El corazón del proyecto. Cada rol ve una aplicación distinta, con endpoints y pantallas protegidas. Un usuario nace como COMPRADOR y puede "darse de alta como vendedor", lo que le añade el rol VENDEDOR (los roles son acumulables).

ROLE_BUYER

Comprador

El rol por defecto al registrarse.

  • Explora el catálogo y filtra productos.
  • Gestiona carrito y checkout simulado.
  • Ve su histórico de pedidos.
  • Deja reseñas y valoraciones de lo comprado.
  • Gestiona su wishlist.
ROLE_SELLER

Vendedor

Comprador que abre su tienda.

  • CRUD de sus propios productos y stock.
  • Panel con métricas (ventas, valoración media).
  • Gestiona los pedidos que recibe.
  • Responde a reseñas.
  • Solo puede tocar lo suyo (regla de propiedad).
ROLE_ADMIN

Administrador

Modera y mantiene la plataforma.

  • Verifica y aprueba vendedores.
  • Gestiona categorías globales.
  • Modera reseñas y productos reportados.
  • Suspende cuentas fraudulentas.
  • Acceso total al backoffice.

La "regla de propiedad" es el reto fino. No basta con que un usuario tenga rol VENDEDOR para editar un producto: debe ser su producto. Eso obliga a seguridad a nivel de método/instancia (más allá del rol), un punto perfecto para lucir en la memoria.

Cómo se construye

Arquitectura de alto nivel

Arquitectura clásica de tres capas desacopladas: una SPA en Angular que consume una API REST en Spring Boot, que a su vez persiste en una base de datos relacional. Una colección NoSQL opcional almacena eventos para analítica.

▸Flujo de una petición protegida

El usuario hace login → recibe un JWT → Angular lo guarda y un interceptor lo adjunta en cada petición → Spring Security valida el token, extrae roles y aplica @PreAuthorize → el servicio comprueba además la propiedad del recurso.

▸Decisiones clave (tradeoffs)

  • Monolito modular y no microservicios: alcance realista para un TFM, más fácil de defender.
  • MySQL para el dominio transaccional; MongoDB solo para eventos (clics/búsquedas).
  • JWT stateless frente a sesiones: encaja con SPA + REST.

El núcleo técnico

Seguridad y autorización (RBAC)

Aquí es donde el proyecto demuestra dominio del Tema 8. Cada endpoint declara qué rol puede usarlo, y los endpoints de modificación añaden además una comprobación de propiedad del recurso.

EndpointMétodoAccesoComprobación extra
/api/productsGETPÚBLICO—
/api/auth/register · loginPOSTPÚBLICO—
/api/cart · /api/checkoutPOSTBUYER—
/api/me/ordersGETBUYERSolo sus pedidos
/api/products/{id}/reviewsPOSTBUYERSolo si lo compró
/api/seller/productsPOSTSELLER—
/api/seller/products/{id}PUT · DELETESELLERProducto de su tienda
/api/admin/shops/{id}/verifyPOSTADMIN—
/api/admin/users/{id}/suspendPOSTADMIN—

▸En el backend

  • SecurityFilterChain con filtro JWT propio.
  • @PreAuthorize("hasRole('SELLER')") a nivel de método.
  • Comprobación de propiedad en el servicio (el producto es de la tienda del usuario autenticado).
  • CORS configurado y manejo global de errores 401/403.

▸En el frontend

  • Guards (CanActivate) que protegen rutas por rol.
  • Interceptor que adjunta el JWT y redirige al login en 401.
  • Menús y botones que se muestran/ocultan según el rol.
  • Lazy loading del módulo de vendedor y del backoffice.

El diferenciador · enfoque teórico

Sistema de reputación y confianza

Este es el capítulo que convierte un e-commerce en un TFM. La pregunta de investigación: ¿cómo genera confianza una plataforma entre dos desconocidos? Se estudia la teoría, se diseña un modelo propio y se compara con plataformas reales.

①Marco teórico

Revisión de los mecanismos de confianza online: valoraciones, reseñas, verificación de identidad, insignias y señales de trayectoria. Cómo cada uno reduce la asimetría de información entre comprador y vendedor.

②Modelo propio

Un score de reputación (0-100) por tienda, combinando valoración media, número de ventas completadas, antigüedad y tasa de incidencias. Pesos configurables y justificados.

③Análisis comparativo

Comparar tu modelo con los de eBay, Wallapop, Etsy y Stack Overflow: ¿qué señales usan?, ¿cómo previenen el fraude y las reseñas falsas?, ¿qué incentivos crean?

Fórmula de ejemplo (a defender en la memoria)

// Score de reputación de una tienda (0-100)
score = 0.40 · ratingMedioNorm // calidad percibida (reseñas)
      + 0.30 · volumenVentasNorm // trayectoria (ventas completadas)
      + 0.20 · antiguedadNorm // veteranía en la plataforma
      - 0.10 · tasaIncidencias // penalización por disputas

▸Insignias (gamificación de la confianza)

  • Vendedor verificado — identidad aprobada por un admin.
  • Artesano destacado — score > 85 sostenido.
  • Respuesta rápida — atiende pedidos en < 24 h.
  • 100 ventas — hito de trayectoria.

▸Prevención de fraude

  • Solo puede reseñar quien ha comprado (reseña verificada).
  • Una reseña por comprador y producto.
  • Detección de patrones sospechosos (muchas 5★ del mismo usuario).
  • Moderación por parte del admin de reseñas reportadas.

Conexión con el temario: el cálculo del score puede hacerse on-read (al consultar) o mediante tareas programadas, y los eventos que lo alimentan (ventas, reseñas) son un caso ideal para el Aggregation Pipeline de MongoDB (Tema 10). La verificación "solo compradores reseñan" ejercita las transacciones y relaciones JPA (Tema 7).

Notas de diseño

▸Identidad

Paleta berenjena + acento dorado, tipografía serif para títulos y sans para interfaz. Transmite artesanía cuidada y cercana.

▸Responsive

Mobile-first: la rejilla pasa a una columna, los filtros se colapsan y la barra lateral del panel se reduce a iconos.

▸Componentes Angular

Cada bloque (card de producto, tarjeta de vendedor, tabla de pedidos) es un componente reutilizable con @Input.

Cómo abordarlo

Roadmap orientativo (M0 → M3)

Una posible planificación en cuatro hitos. La idea es tener algo funcional pronto y dejar el twist de reputación y los tests para el final, cuando el dominio ya es estable.

Semana 1 · M0 — Cimientos

Setup y autenticación

Proyecto Spring Boot + Angular, Docker Compose (api + MySQL), entidad User, registro/login con JWT y los guards básicos en Angular. Objetivo: poder registrarse e iniciar sesión.

Semanas 2-3 · M1 — Catálogo y tiendas

Productos, categorías y rol vendedor

CRUD de productos, alta como vendedor (tienda), explorador con filtros, fichas de producto. Aquí se materializa la seguridad por roles y la regla de propiedad.

Semana 4 · M2 — Compra y reseñas

Carrito, checkout simulado y valoraciones

Carrito, pedido con estados, histórico del comprador, panel del vendedor con sus pedidos, y reseñas verificadas (solo quien compró).

Semanas 5-6 · M3 — Twist + calidad

Reputación, tests y memoria

Sistema de reputación con su score e insignias, panel de admin (verificar vendedores, moderar), batería de tests (JUnit + Karma), CI y redacción del análisis comparativo de la memoria.

Consejo: valida este alcance con tu tutor antes de empezar. El marketplace es ambicioso; si vas justo de tiempo, una buena estrategia es recortar el panel de admin a lo mínimo (verificar vendedores) y concentrar el esfuerzo en el sistema de reputación, que es lo que da valor académico.
